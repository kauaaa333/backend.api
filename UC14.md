# TaskFlow API — UC14, Dias 1, 2 e 3

> Atualização de 29/10/2026: este documento descreve as etapas anteriores. A implementação atual usa Prisma também nas gravações e na autenticação, e conflitos de exclusão por vínculos retornam 409. Consulte `PRISMA.md` e `VALIDACAO_UC14_DIA8.md` para o estado atual, testes e publicação.

Os PDFs tratam do servidor Express e da integração com o front-end. As alterações foram adaptadas ao contrato atual desta API.

## Implementado

- `src/utils/criarErro.js`: erro operacional com status, mensagem e detalhes opcionais.
- `src/middlewares/erro.middleware.js`: resposta única `{ "erro": { "mensagem": "...", "detalhes": [] } }`. O campo detalhes aparece somente quando informado. Falhas inesperadas retornam `500` e `Erro interno no servidor`, sem detalhes técnicos. As violações conhecidas de integridade do PostgreSQL continuam traduzidas em `400` ou `409`.
- Controllers, autenticação e comentários encaminham erros para o mesmo middleware.
- IDs de tarefas, usuários, projetos e comentários são inteiros positivos, validados antes dos controllers. Os filtros `usuarioId`, `projetoId` e `coluna` também são validados.
- A validação aceita `body`, `params` e `query`; lida com corpo ausente e campos opcionais; informa os problemas em `erro.detalhes`.
- Rotas inexistentes retornam `404` em JSON. Ordem: rotas → erro 404 → middleware de erros.
- Criação retorna `201`; consulta/atualização retorna `200`; exclusão de tarefas, usuários, projetos e comentários retorna `204` sem corpo.
- Collection Postman exportada com login, CRUD e casos de erro; ambientes Local e Produção.

## Adaptações ao projeto

Os exemplos da aula usam `usuario_id` e `projeto_id`. Aqui a API recebe **`usuarioId` e `projetoId`** e os models fazem o mapeamento para o banco. Alterar esses nomes quebraria os clientes existentes.

No POST de tarefa, somente `texto` é obrigatório. A API identifica o usuário pelo login e aplica os padrões existentes (`afazer`, prioridade média e projeto opcional). Assim, `{}` retorna os detalhes do campo `texto`, em vez dos cinco erros do exemplo dos slides.

O PUT continua permitindo atualização parcial para preservar a movimentação do Kanban. Campos obrigatórios omitidos são mantidos; se enviados vazios, são recusados. PUT sem nenhum campo reconhecido retorna `400`. Essa é uma adaptação deliberada em relação ao exemplo da aula, que exige todos os campos no PUT.

Foram preservadas as permissões, consultas ao Neon, auditoria e limite de duas tarefas em andamento. Banco, migrations e credenciais não foram alterados por esta implementação.

## Postman

1. Inicie a API com `npm run dev` (porta `3001`, conforme `PORTA=3001` já definido no projeto; sem configuração, o servidor usa `3000`).
2. Importe `postman/TaskFlow-UC14.postman_collection.json` e os dois arquivos de ambiente.
3. Selecione **TaskFlow — Local** e preencha `email` e `senha` com uma conta existente no seu banco.
4. Rode a coleção completa. Ela faz login, captura o token, cria registros temporários, testa e exclui esses registros. A pasta Usuários usa uma sessão própria para o usuário temporário, respeitando as permissões.
5. Para produção, confira `baseUrl` no ambiente **TaskFlow — Producao**. O valor exportado corresponde à URL configurada no front-end. Preencha as credenciais no Postman.

O Runner altera dados: execute a coleção inteira em uma base de desenvolvimento. Se uma execução falhar antes da limpeza, podem restar registros com o prefixo `Teste UC14` ou `UC14`. O valor `idInexistente` é configurável na coleção, caso o ID escolhido exista no seu banco.

Não há credenciais reais ou tokens exportados. As instruções dos slides para push/deploy não foram executadas; os arquivos foram preparados localmente.

## Verificação

- `npm run test:uc14`: testes HTTP com Express real e models simulados, sem conexão com banco. Incluem validação, 404, JSON inválido, status de sucesso e falha interna simulada.
- `npm test`: testes UC14 mais a suíte existente com Neon. A preparação existente exige uma branch isolada e confirma seu host antes de limpar os dados de teste.

Para simular banco indisponível, o teste UC14 lança uma falha no model. Não é necessário corromper a `DATABASE_URL` do projeto, como sugerido no exercício manual.

Verificação desta implementação: 57 testes da API aprovados; coleção executada pelo Newman na branch isolada do Neon com 37 requisições e 63 verificações aprovadas. A coleção não foi executada em produção.

## Dia 3 — selects e erros na interface

- `GET /prioridades` aplica `WHERE ativo = true`, com parâmetro SQL. As estatísticas continuam considerando todas as prioridades, inclusive históricas.
- O front carrega `/tarefas`, `/prioridades`, `/usuarios` e `/projetos` com `Promise.all`, respeitando o acesso aplicado pela API.
- O formulário envia `usuarioId`, `projetoId` e `idprioridade` numéricos, e mostra `erro.detalhes` em uma lista. Não envia CEP/cidade.
- Um PUT somente com o campo legado `prioridade` também é reconhecido pelo schema.
- O filtro `usuarioId` passou a ser aplicado às estatísticas e ao ranking retornado.
- O banco mantém projeto opcional, prioridade Média ID 3 e PUT parcial. Não copiar os nomes snake_case nem os três IDs fixos do exemplo do slide.
- A verificação de 21/10/2026 aprovou 59 testes da API na branch isolada `teste-status-seguranca-20261013`. Os dois testes novos conferem prioridades inativas e persistência diretamente no PostgreSQL.
- Os cenários de navegador foram exercitados com a API local conectada a essa mesma branch, sem limpar a produção.
